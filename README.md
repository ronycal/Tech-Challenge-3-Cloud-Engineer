# Cloud Engineer Coding Challenge 3: Infrastructure as Code with Terraform and Ansible

This project provisions and configures a web server environment on AWS using Terraform and Ansible.

## Overview

Terraform is used to provision the AWS infrastructure, including networking, compute, IAM, and S3 resources. Ansible is used to configure the EC2 instance, install and manage Nginx, and deploy a custom web page.

The project demonstrates:

- Infrastructure as Code using Terraform
- Configuration management using Ansible
- AWS VPC networking and security groups
- EC2 instance provisioning
- IAM roles and instance profiles
- S3 bucket provisioning and access control
- Automated Nginx installation and configuration
- Ansible idempotency
- Git version control

## Architecture

The environment uses a dedicated AWS VPC with a public subnet for the web server.

```text
Internet
   |
   v
Internet Gateway
   |
   v
Public Route Table
   |
   v
Public Subnet
   |
   v
Security Group
   |
   v
EC2 Instance
   |
   v
Nginx Web Server

EC2 Instance
   |
   v
IAM Instance Profile
   |
   v
IAM Role
   |
   v
S3 Bucket
```

### Network Design

- Dedicated VPC: 10.0.0.0/16
- Public subnet with automatic public IP assignment
- Internet Gateway attached to the VPC
- Public route table with a 0.0.0.0/0 route through the Internet Gateway
- Security group allowing HTTP on TCP port 80
- SSH on TCP port 22 restricted to the administrator workstation's public IP
- Outbound traffic allowed from the EC2 instance

### AWS Resources

Terraform provisions the following resources:

- VPC
- Public subnet
- Internet Gateway
- Public route table and route table association
- Security group
- Amazon Linux 2023 EC2 instance
- S3 bucket with versioning enabled
- S3 public access block
- IAM role
- IAM policy granting the EC2 instance access to the project S3 bucket
- IAM instance profile

## Deployment

### 1. Provision the AWS Infrastructure

Navigate to the Terraform directory:

```bash
cd terraform
```

Initialize Terraform:

```bash
terraform init
```

Validate the configuration:

```bash
terraform validate
```

Review the execution plan:

```bash
terraform plan -out=tfplan
```

Apply the infrastructure:

```bash
terraform apply tfplan
```

Terraform creates the AWS infrastructure and outputs the EC2 public IP address, public DNS name, S3 bucket name, and website URL.

### 2. Configure the EC2 Instance with Ansible

Update `ansible/inventory.ini` with the public IP address produced by Terraform.

Navigate to the Ansible directory:

```bash
cd ../ansible
```

Test connectivity:

```bash
ansible -i inventory.ini all -m ping
```

Validate the playbook:

```bash
ansible-playbook -i inventory.ini playbook.yml --syntax-check
```

Run the playbook:

```bash
ansible-playbook -i inventory.ini playbook.yml
```

The playbook:

- Installs Nginx
- Starts and enables the Nginx service
- Deploys the custom Hello World webpage

## Verification

After Terraform provisions the infrastructure and Ansible configures the EC2 instance, connectivity and application functionality can be verified.

### Verify Ansible Connectivity

```bash
ansible -i inventory.ini all -m ping
```

A successful connection returns:

```text
SUCCESS => {
    "changed": false,
    "ping": "pong"
}
```

### Verify the Web Server

The deployed website can be tested with:

```bash
curl http://<EC2_PUBLIC_IP>
```

The expected page contains:

```text
Hello, World!
Deployed with Terraform and Ansible.
```

The website can also be accessed from a web browser using the `website_url` output generated by Terraform.

## Ansible Idempotency

The Ansible playbook is designed to be idempotent. After the server reaches the desired state, running the playbook again should not make unnecessary changes.

```bash
ansible-playbook -i inventory.ini playbook.yml
```

A subsequent execution should report:

```text
changed=0
unreachable=0
failed=0
```

This confirms that Ansible recognizes the existing configuration and only makes changes when the desired state differs from the current state.

## Security

The project implements several security controls:

- SSH access is restricted to an administrator-defined CIDR rather than `0.0.0.0/0`.
- HTTP access is allowed on TCP port 80 for the public web server.
- The S3 bucket blocks public access.
- S3 bucket versioning is enabled.
- EC2 accesses S3 through an IAM role and instance profile rather than stored AWS credentials.
- The IAM policy limits S3 access to the project bucket.
- Terraform variable files, state files, plan files, and SSH private keys are excluded from Git.
- SSH private keys are not stored in the repository.

## Cleanup

To avoid unnecessary AWS charges, destroy the infrastructure when it is no longer needed.

From the `terraform` directory:

```bash
terraform plan -destroy
```

Review the destruction plan carefully, then run:

```bash
terraform destroy
```

Confirm the destruction when prompted.

After completion, Terraform should report that the managed resources were destroyed.

## Troubleshooting and Lessons Learned

### EC2 Instance Type and Free Tier Eligibility

The initial EC2 deployment failed because the selected instance type was not eligible for the AWS Free Tier in the target region.

Free Tier eligible instance types were identified using the AWS CLI, and the configuration was updated to use `t3.micro`.

This demonstrated the importance of validating instance-type availability and account-specific Free Tier eligibility before deployment.

### SSH Connectivity Timeout

After the initial deployment, the EC2 instance was running and the security group allowed SSH from the administrator workstation, but connections to TCP port 22 timed out.

Connectivity was tested using:

```bash
nc -vz -w 5 <EC2_PUBLIC_IP> 22
```

and from Windows using:

```powershell
Test-NetConnection <EC2_PUBLIC_IP> -Port 22
```

The security group was verified and correctly allowed SSH from the administrator's public IP.

Further investigation of the VPC route table revealed that the default route:

```text
0.0.0.0/0
```

pointed to an Internet Gateway whose route state was:

```text
blackhole
```

The Internet Gateway existed but was not attached to the VPC.

### Network Architecture Correction

The Terraform configuration was updated to explicitly manage:

- A dedicated VPC
- Public subnet
- Internet Gateway attached to the VPC
- Public route table
- Default route through the Internet Gateway
- Route table association
- Security group associated with the dedicated VPC

After applying the corrected Terraform configuration, the default route reported:

```text
0.0.0.0/0 -> Internet Gateway -> active
```

TCP port 22 then became reachable, SSH connectivity succeeded, and Ansible was able to manage the EC2 instance.

### Key Takeaways

- A running EC2 instance and correct security group do not guarantee network connectivity.
- Route tables and Internet Gateway attachments must also be validated.
- Terraform should explicitly manage networking dependencies instead of relying on assumptions about the default VPC.
- Infrastructure should be validated layer by layer when troubleshooting connectivity.
- Ansible idempotency provides a reliable way to maintain the desired server configuration.
